SECTION 2   ·   SUBSECTION 2.1
SCOPE, ARCHITECTURE AND READING MAP
2.1.1

SCOPE AND OPERATING PRINCIPLE.

Pi-durable is an experimental agent harness built over pi-ai model access and Chord document state. Its durable unit is a committed change to entries, documents and task state, not a suspended JavaScript stack. Reopening the same persistent storage reconstructs unfinished work from checkpoints. External effects remain outside that commit boundary; a recorded tool intent does not prove that a remote service acted exactly once.

This handbook describes packages/durable at main snapshot 479d6e5e298821088cfd77566a139097e73a888b, dated 27 October 2026. The source manifest says 1.4.0. That is not evidence that a published npm release contains this snapshot. The report explains implementation and operating contracts, not benchmark results or a certification of backend durability.

2.1.2

LAYER RESPONSIBILITIES.

The host chooses models, installs a registry, supplies an execution environment and owns storage exclusively. Harness opens a Session and supplies its scheduler with guarded storage and task definitions. Conversation handles address transcript branches; they are not independent state containers. Session serializes commits and adopts stored batches into memory before normal publication. Storage implements the backend-specific atomic operation.

A generation task calls the model. Tool calls become owned tool tasks, and a generation waits for that round before continuing. Ownership is a durable relation used for joins, abort propagation and cleanup. A tool reaches files or processes through its environment; installing its definition alone does not provide those capabilities.

4–5What resumes, blocks or sleeps?TaskState; scheduler recovery and wake control
6–7What can execute again?Tool intent; replay policy; nested receipts

2.1.3

A REPRESENTATIVE INTERRUPTION.

An input is admitted, a generation emits a tool call, and the tool stores its final arguments and replay policy before execution. If the process disappears after an external write but before the result commit, reopening can find the intent without finding a receipt. It can neither infer that the write failed nor undo it. The recovery rule on sheet 6 selects rerun or interruption; the host must reconcile any uncertain external mutation.

Live partial answers are a separate, deliberately weaker channel. Watches may receive deferred progress before storage receives it. Therefore the architecture has a durable decision path and a provisional display path, not a universal rule that every visible byte was already persisted. Sheet 9 distinguishes these paths and the evidence each supplies.

SECTION 2   ·   SUBSECTION 2.1
MINIMAL INTEGRATION AND CANCELLATION
2.1.4

OPEN, SUBMIT, WAIT, CLOSE.

The following host composition uses Node SQLite. It assumes models already contains a configured provider and modelRef identifies an available model. Every asynchronous public operation receives a Chord Context; BACKGROUND_CONTEXT never cancels and carries a no-op telemetry span. Provider credentials belong in the host environment, not in stored agent state.

import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { AssistantEntry, createRegistry, Harness } from "@earendil-works/pi-durable";
import { openNodeSqliteStorage } from "@earendil-works/pi-durable/storage/sqlite/node";
const context = BACKGROUND_CONTEXT;
const harness = await Harness.open(await openNodeSqliteStorage("./session.sqlite"),
  { models, registry: createRegistry() }, context);
try {
  const root = await harness.root(context, { agent: { model: modelRef } });
  const submission = await root.submit({ type: "input", content: "Hello",
    requestId: "greeting-1" }, context);
  const settled = await submission.wait(context);
  if (settled.status === "done" && settled.type === "input")
    console.log(await root.commit(tx => tx.entry(AssistantEntry, settled.answer), context));
} finally {
  await harness.close(context);
}
2.1.5

ADMISSION IS NOT COMPLETION.

Harness.open opens the backend-backed Session and performs recovery. root returns the existing root or creates it on first use; the supplied agent choices apply to that creation. submit durably admits an input and returns a Submission. Its wait resolves to a completed admission/answer or an unanswered result with a reason. Code must inspect the settlement instead of treating every resolved promise as an assistant answer.

Reopening does not by itself dispatch recovered work. harness.resume() starts scheduling; submitting or waiting starts it too. A host that only opens a session and exits can leave pending tasks untouched. To reconnect after an uncertain response, reuse a stable requestId or reacquire a known admission through harness.submission(id, context); generating a new ID on each transport retry defeats deduplication.

Table 2.1-2. Cancellation Boundaries
OperationWhat cancellation means
submission.wait(context)Cancels that wait, not the admitted work.
submission.abort(context)Withdraws a queued admission.
root.abort(context)Stops ordinary current work; queued inputs withdraw, queued writes stay.
harness.close(context)Interrupts runtime work; unfinished work remains recoverable.
Storage settlement already admittedCaller cancellation does not interrupt its settlement.
2.1.6

UNCERTAIN RETURN HANDLING.

A client disconnect can occur after admission but before the response reaches the client. The correct retry is the same requestId in the same conversation, followed by inspection of that submission. Cancelling the disconnected request context is not an application-level undo. Likewise, cancellation during a commit is not proof that no write occurred once the storage operation has been admitted.

Use finally for close when this process owns the Harness lifetime. A long-lived server normally keeps one open instance rather than opening competing owners per HTTP request. A read-only viewer uses readOnly: true; it does not recover tasks, and attempts to write or start scheduling reject with ReadOnlySession. Viewing and driving are distinct operating roles.

SECTION 2   ·   SUBSECTION 2.1
ENTRIES, DOCUMENTS AND ATOMIC COMMITS
2.1.7

ENTRIES AND DOCUMENTS.

An entry is an immutable transcript record. Built-in kinds include pi.user, pi.assistant, pi.tool-result, pi.system and pi.reset. A document is typed JSON state beside that transcript. It changes through commits rather than by mutating a Conversation handle.

The built-in documents separate agent configuration (pi.agent), provider session identity (pi.provider), live work (pi.live), queued admissions (pi.inbox) and usage (pi.usage). Application documents specify scope, schema version, history policy, fork policy and checkpoint selection. These policies govern historical reads and branch state.

import { defineDoc } from "@earendil-works/pi-durable";
const Todos = defineDoc<{ items: string[] }>({
  kind: "app.todos", version: 1, scope: "conversation",
  history: "latest", fork: "initial", initial: () => ({ items: [] }),
  checkpointWhen: () => false
});
await root.commit(async tx => {
  (await tx.doc(Todos, root.id)).items.push("write docs");
}, context);
const saved = await harness.snapshot(Todos, root.id, context);
2.1.8

ATOMIC DECISION BOUNDARY.

A conversation commit can append entries, change documents and create tasks together. Session executes the callback, settles its staged writes, and sends the resulting batch to Storage. A callback failure discards its staged changes. For a normal stored commit, memory changes and publication occur through adoption after the backend has committed. Thus a task decision and the transcript evidence that explains it need not be separate writes.

The atomicity applies to the stored batch. Network requests or shell commands in the callback are not part of that transaction. Stage durable changes there; do not expect rollback of outside effects. Storage failure normally fails the Session; invalid or caller-cancelled reads fail only that read. A failed Session must be reopened.

Table 2.1-3. Document Design Decisions
ChoiceConsequence
history: "latest"Keeps the current value; does not promise historical snapshots.
history: "rewindable"Enables historical reads through snapshotAsOf().
fork: "initial", "current", "asOf"Selects initial, current or fork-point state for a branch.
checkpointWhenStores selected changes as complete bases to bound replay.
2.1.9

STORAGE ADOPTION CONTRACT.

Storage is not just an append function that eventually updates a cache. Its commit contract includes synchronous adoption of the durable batch before a later commit can overtake it. SQLite writes entries, documents and tasks in one database transaction, then invokes adoption after COMMIT. A custom backend must preserve this ordering as well as atomic writes and consistent reads.

The sample follows the README. A growing operation history needs a deliberate checkpoint policy. Historical fork state requires compatible history and fork policies.

SECTION 2   ·   SUBSECTION 2.1
TASK STATES, OWNERSHIP AND OUTCOMES
2.1.10

CHECKPOINTED EXECUTION.

A durable task is a named, versioned state machine with JSON input and checkpoint state. A phase starts at the checkpoint; it does not resume at an arbitrary await expression. Each phase must change its checkpoint, park, or commit an outcome; document-only progress does not suffice. Work after a wait belongs in a later phase with the required checkpoint data. A task can own child tasks and conversations, providing a stored tree rather than an in-memory collection of promises.

Table 2.1-4. The Six Durable States
StateMeaning and next action
pendingEligible for invocation, unless derived blocking prevents dispatch.
runningReserved by an in-memory invocation; checkpoint remains recoverable.
waitingNo invocation; waits for tasks in on under its join policy.
sleepingNo invocation; resumes when the Harness clock reaches until.
completingOutcome decided; no more task code; drains ordinary owned work.
terminalSettled outcome; no further task code.
2.1.11

OUTCOMES DESCRIBE WHY WORK ENDED.

TaskState and TaskOutcome answer different questions. The state says whether work can run, waits, drains or has settled. The outcome records completed, failed, aborted, orphaned or faulted. Failed is an expected domain or task failure explicitly committed by its implementation. Faulted is a runtime contract failure, such as an uncaught throw or a phase that makes no durable progress. Aborted records the explicit cancellation protocol, not a guarantee that external effects were reversed.

An explicit abort with unavailable definition or migration can settle a task orphaned. A missing definition normally blocks live work, awaiting registry repair. Installing code may unblock live work; it cannot revive a terminal orphan receipt.

Table 2.1-5. Outcome Interpretation
OutcomeOperator interpretation
completedRead the typed result; task protocol completed.
failedInspect the stored domain error and optional result.
abortedCheck reason and external effects; cancellation is not rollback.
orphanedDefinition/migration cannot support continuation.
faultedInspect implementation or abort-handler contract failure.
2.1.12

OWNED WORK AND JOINS.

A parent does not become fully terminal while ordinary owned work remains live below it. The completing state holds its chosen outcome during that drain. Waiting, by contrast, retains a checkpoint and explicitly resumes task code after its dependency condition is met.

For example, a checkout task can create payment children and return a durable join decision rather than keeping an invocation alive. A child that reports a declined card has a failed domain outcome; a child whose phase throws has faulted. The parent uses the join policy and child receipts to decide its own result. Terminal does not necessarily mean completed.

SECTION 2   ·   SUBSECTION 2.1
SCHEDULER RECOVERY, PARKING AND WAKE CONTROL
2.1.13

RECOVERY IS SEPARATE FROM DISPATCH.

One host owns a storage at a time. The package supplies no cross-process lease or writer election. On open, the scheduler recovers interrupted running tasks to pending while preserving their checkpoints. Only then does resume, submit or a wait enable dispatch. The host can inspect uncertain work before allowing effects.

Read-only open performs no recovery. In a browser, ownership must cover tabs and workers as well as processes; the README recommends a Web Lock for the IndexedDB lifetime. Transaction isolation does not reconcile two independent schedulers.

2.1.14

PARKING REPEATED CUTOFFS.

Deterministic resource failure can kill a process before its checkpoint. Recovery counts interrupted invocations without changed durable state. The default restartLimit is 5; a clean close is not counted, and committing a new state resets the count. Reaching the limit parks the task with blocked reason restart_limit. Parking is derived scheduler state, not a seventh durable TaskState.

wake does not count parked work as active. inspect and the task graph expose the block; onReport emits task_parked. After repairing the cause, harness.retryTask(id, context) permits another attempt. abortTask still runs cleanup; an abort handler cut off at the same threshold ends faulted. Every running task counts; a parked task need not have caused the failure.

// Reopen only after excluding competing owners and restoring definitions.
const harness = await Harness.open(storage, { models, registry }, context);
const inspection = await harness.inspect(context);
const wake = harness.wake();
// Host reviews blocked work and uncertain external effects here.
harness.resume();
2.1.15

DURABLE TIME RATHER THAN SUSPENDED TIMERS.

runtime.sleepUntil(until, checkpoint, context) stores a sleeping state and ends the phase. When due, dispatch begins at the named checkpoint. Retry backoffs use the same mechanism. The timestamp is in milliseconds on HarnessOptions.now, whose default is Date.now. All owners reopening that storage must use the same clock domain; changing an epoch can turn a sensible deadline into an immediate or indefinite wait.

Session, scheduler and task timers use setTimer, defaulting to setTimeout. Inject both for controlled-clock testing; environment, file watcher and image worker timers remain separate. A sleeping task holds no invocation; with ordinary scheduling enabled, the wake timer keeps a Node process alive until due.

Table 2.1-6. Evictable Host Wake Contract
Signal or actionHost responsibility
onWake installedHarness does not arm its own task-sleep timer.
wake.activeSome work can run now or is running; maintain a recovery wake.
wake.atEarliest durable sleep; do not arm later than it.
Before an operation that can start workArm a fallback before admission; onWake follows the commit.
Alarm firesRe-arm as needed and call resume().
2.1.16

A STRANDED-WORK DIAGNOSIS.

If a reminder remains sleeping after process eviction, first compare its stored until with the current clock. Then inspect the host alarm rather than retrying the tool. An early alarm is harmless; a missing alarm can strand work even though its checkpoint is sound. If open itself can fail, arm a fallback before opening. A scheduling library cannot wake an evicted process without host cooperation.

The Durable Object heartbeat is host-selected, not a Harness interval. Handle alarm-write failure and preserve the recovery wake before starting work.

SECTION 2   ·   SUBSECTION 2.1
TOOL INTENT, REPLAY AND EXTERNAL EFFECTS
2.1.17

INTENT BEFORE EXECUTION.

Each tool call is a durable pi.tool task. Its call phase resolves the enabled tool, prepares and validates arguments, runs beforeTool hooks, then validates again after any rewrite. It records the final JSON arguments and the tool replay declaration, defaulting to unsafe, at an execute checkpoint before entering the implementation. A blocked or invalid call settles without executing the tool.

The stored intent answers what was authorized to run, not whether the external action finished. Process loss between those records leaves an uncertainty interval, even when the external service returned successfully before the process disappeared. Local atomic commits cannot join an arbitrary external service transaction.

2.1.18

BOTH DECLARATIONS MUST PERMIT REPLAY.

The recovery execute phase resolves the current tool and reruns only if the stored policy and the current implementation both say safe. Making an unsafe tool safe after a crash cannot retroactively authorize replay of its old intent. Replacing a formerly safe implementation with an unsafe one also prevents rerun. If both permit replay, progress from the interrupted attempt is cleared and execution begins again with the saved final arguments.

Recovery does not repeat admission-time preparation and beforeTool hooks. Current tool availability and environment still matter when execution is resolved. If replay is refused, the result reports interrupted and says the tool may have partially run. That diagnostic proves neither rollback nor remote failure.

Table 2.1-7. Crash Position and Evidence
Last durable evidencePossible external stateSafe interpretation
No execute intentImplementation has not entered through this intent.Repair admission/validation, not an assumed completed effect.
Intent, no resultNo effect, partial effect, or complete effect are possible.Apply replay policy; reconcile uncertain mutations.
Committed resultA local result receipt exists.Reuse the receipt; do not infer reversibility.
Only recent live outputDisplay may exceed persisted progress.Use durable receipt/checkpoint for control decisions.
2.1.19

DESIGNING A REPLAY-SAFE MUTATION.

A remote mutation needs its own idempotency boundary. One design supplies a stable operation key derived from durable application identity; the service records that key and returns the same result on repetition. Another uses compare-and-set against a known resource version. These are host/tool design techniques, not automatic properties of replay: "safe". A retry that generates a fresh key inside execute can still duplicate the effect.

For example, a deployment request can be accepted remotely while the local process loses its response. A repeated query by the same deployment key may recover the original operation. Blindly sending a second unkeyed deployment cannot. Marking the tool safe is justified only if rerunning its complete implementation, including preparatory and follow-on effects, tolerates this sequence. Read-only calls that consume one-shot tokens also need scrutiny.

SECTION 2   ·   SUBSECTION 2.1
NESTED RECEIPTS, REGISTRY AND ENVIRONMENT
2.1.20

NESTED CALLS ARE DURABLE CHILDREN.

A tool can call another tool through api.executeTool. The child is independently validated, runs ToolTask hooks and has its own output limits and replay policy. Its result returns to the parent rather than becoming a separate model transcript result. Hooks can inspect call.parent to distinguish a script or bridge call from a model-issued call. The durable owner edge connects their lifetimes.

A nested call key defaults to its position among the parent calls; the caller can instead supply an explicit key. Repeating that key reattaches to the existing child only when the tool name and arguments match. Reusing a key with changed arguments is an error, not a new request. Stable explicit keys are useful when application control flow makes call order a fragile identity.

const run = await api.executeTool("bash", { command: "npm test" }, context,
  { key: "test-suite", progress: false });
const exitCode = (run.structuredOutput as { exitCode: number } | undefined)?.exitCode;
// A nonzero exit is an error result; inspect it, not just promise resolution.
2.1.21

TWO DIFFERENT RECOVERY MECHANISMS.

A completed child result in NestedCallDoc is a receipt: a replay-safe parent can obtain it again without another child execution. A child interrupted before its result commit has no such receipt and follows its own replay policy. Thus a safe parent does not make an unsafe child safe. Before a parent settles, children it left running are aborted, including those created by an earlier attempt.

Nested result documents belong to the parent and are retained only until it settles; the child task keeps a small receipt. The returned structuredOutput, diagnostics, details, usage and isError are the program interface, distinct from model output. Child usage is counted under the child tool; returning that usage again as the parent usage double counts it. Parents that cannot replay automatically abandon their unfinished nested work on restart before it can run again.

2.1.22

REGISTRY AND EXECUTION ENVIRONMENT.

The registry holds code in memory. Conversations store selected extension and tool names in pi.agent, not executable objects. An extension can provide tools, sections, hooks, wrappers and task definitions. Installing the same extension name replaces it in place. An already-running call keeps its implementation; later phases, requests and calls resolve from the current registry. After restart the host must install the required definitions again.

The environment factory receives the conversation identity, current working directory and committed reads. Built-in file/process tools require an environment and fail without one. Equal ExecutionEnv ids must mean the same paths address the same files, because write/edit serialization uses environment id plus path. A replacement container must not casually reuse an id for unrelated storage.

modelToolsNarrows what the model is offered; does not grant tools.
callersPermits model, nested tools, or both.

SECTION 2   ·   SUBSECTION 2.1
CONVERSATION ADMISSIONS, RESET AND FORK
2.1.23

ADMISSION IDENTITY AND BUSY POLICY.

A requestId identifies a submission within its conversation. Reusing it returns the existing submission instead of admitting another input; it is not a global external-effect key. Keep the same ID across uncertain transport retries and store the returned submission ID when a client needs to reconnect. Do not recycle an ID for new content.

A conversation is busy while a run works on an input. Default input submission is a follow-up, queued in pi.inbox until that run answers. whenBusy: "steer" joins the current work after the tool round. whenBusy: "reject" throws ConversationBusy instead of queuing. These are transcript placement policies.

await root.submit({ type: "input", content: "Also test it",
  requestId: "follow-up-1" }, context);
await root.submit({ type: "input", content: "Use pnpm",
  whenBusy: "steer", requestId: "steer-1" }, context);
await root.submit({ type: "input", content: "Only if idle",
  whenBusy: "reject" }, context);
await root.submit({ type: "write",
  entry: { kind: "app.note", data: "file opened" } }, context);
2.1.24

PLACEMENT DETERMINES TRANSCRIPT ORDER.

Steers land after current tools, whereas follow-ups wait for the answer and begin the next run. A plain application write with only kind and data can append immediately even while busy because it changes nothing the model sees. It can therefore appear before an older queued input. A write with model, head or edits waits for the next boundary. Behind a queued reset, even a plain write waits so that the reset cannot hide it.

If a run fails, the default leaves queued inputs waiting until a later input or queued write places them. afterFailedRun can instead continue them or withdraw them as unanswered with run_failed. Display queued state separately from provider-visible input. submission.abort withdraws a queued item; root.abort stops ordinary current work and withdraws queued inputs but leaves queued writes; background roots require explicit inclusion.

Table 2.1-9. Context-Changing Operations
OperationTranscript and run effect
reset(undefined, context)New model context; older stored entries remain.
reset(handoff, context)New context begins with the supplied handoff.
Busy queued reset placedCurrent inputs become unanswered/reset; queued inputs use new context.
Tool control.handoffWrites reset text but normally continues the same run.
fork(entryId, { ownership }, context)New independent branch through the selected entry.
2.1.25

FORK STATE IS A HISTORICAL CHOICE.

A fork shares its parent transcript up to the chosen entry and then continues independently. It takes the agent configuration as of that entry and receives a fresh provider session identity. Document fork policies independently select initial, current or historical state. Shared transcript history does not imply copied current documents.

reset() resolves on admission, not necessarily placement of a queued reset. Reset is not deletion. It changes what the model sees once placed; stored older entries remain available to history and inspection. Compaction likewise reduces the active context without erasing prior entries. Neither operation sanitizes previously transmitted content from a provider or removes external side effects. A retention or erasure requirement needs a separate storage and provider policy.

A handoff returned by a tool differs from a queued reset: it can keep the current submission alive until an eventual answer. If every tool in the round also requests terminate, the run ends after that handoff. Associate answers with submissions, not merely the newest entry.

SECTION 2   ·   SUBSECTION 2.1
PROGRESS, COMPACTION, RETRIES AND TELEMETRY
2.1.26

PROVISIONAL PROGRESS AND DURABLE EVIDENCE.

pi.live contains partial generation output, tool progress, retry state and compactions. The default partial/output publication intervals are 100 ms; default deferred persistence targets 1000 ms. Watches can receive this progress before storage receives it. Phase boundaries and dependent reads flush held changes. Timers and backend behavior prevent treating the target as a hard loss or latency bound.

A crash can lose recent output while retaining tool intent. A stream interrupted before any partial is persisted may leave no aborted entry or usage for that attempt. Recorded usage need not cover every provider-side charge. Recorded failed attempts count; callers must not double-count nested usage.

const watch = await root.watch(context);
render(watch.value);
watch.start(async ({ value, ops }) => { render(value); await send(ops); });
// send is a host-defined transport; progress may be provisional.
// Later: await watch.stop();
const usage = await harness.usage(context);
2.1.27

WATCHES ARE STATE DELIVERY, NOT AN EVENT LEDGER.

A watch starts with current state. During its listener, later commits fold into the next view and operations. Past 10,000 pending operations, delivery becomes a root replacement. Reconnect starts at current state, not historical callbacks. Consumers must support replacement and apply operations to their acquired base.

watchEvents derives coding-agent-style event batches from commits and supplies an initial snapshot. Beyond 100 pending batches, the consumer receives a fresh snapshot. Synchronous observers are a lower-level integration boundary: advance must be quick, must not await or call the Harness, and must not throw. They participate in adoption, so blocking one blocks commit progress.

2.1.28

COMPACTION AND MODEL RETRIES.

Compaction summarizes older entries and appends pi.compaction while preserving stored history. The summary is prepared concurrently and placed immediately if idle or at a turn boundary if busy. A superseded summary settles stale. A blocking compaction failure fails the waiting generation before a model request; a declined compaction or one with nothing to summarize lets the request proceed.

Automatic defaults reserve 16384 tokens, keep approximately 20000 recent tokens and start background compaction 32768 tokens below the blocking threshold. modelOverrides adapts these policy constants per provider/model. A context-overflow rejection can trigger compaction and one retry when enabled and a valid cut exists. Ordinary retry policy does not retry overflow. The separate durable generation retry budget defaults to 3 with a 2000 ms base delay; provider/SDK HTTP retries are another layer.

2.1.29

PRIVACY AND INCIDENT EVIDENCE.

Telemetry is host-owned and otherwise a no-op. Attributes use IDs/control metadata, not messages, arguments or results. Phase error diagnostics can still contain caller content, with recorded messages truncated to 500 characters.

Persistent storage permits reopen after process loss, but backend durability differs. Choose among process-crash recovery, host-loss resistance, browser retention and evictable-host wakeup.

FAILURE DIAGNOSIS BY DURABLE SYMPTOM.

Start from the last stored decision rather than the last text rendered. If the Session failed after a Storage error, exclude other writers, repair the backend and reopen rather than using the failed instance. If a task is blocked by a missing definition, restore its extension/migration; resume cannot supply code. If restart_limit is reported, investigate deterministic process failure before retryTask.

Sleeping points to the clock/alarm; waiting to dependency receipts/join policy; completing to undrained owned work. Execute intent without result points to replay and external reconciliation, not necessarily model failure. Queued follow-ups after model failure may be normal.

EXPLICIT LIMITS AND ACCEPTANCE CHECKS.

No exactly-once external execution, cross-process lease, universal HTTP attempt limit, hard progress-loss bound or performance is promised. Replay safety requires implementation design. Reset/compaction retain history. Registry code is not persisted; provider identity is not a lease; abort is not rollback.

Test loss around tool intent/result commits, repeated requestId, missing definitions, parking and overdue sleeps. On evictable hosts, test post-admission loss and alarm-write failure. Run conformance helpers for custom backends/environments and application failure tests. The source was inspected for this handbook; package tests and performance benchmarks were not run.
